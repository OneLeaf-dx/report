# YOLO26-nano-P2 即時辨識採用門檻實機測試報告

> **報告日期**：2026-09-13（量測日期 2026-09-11）
> **評測對象**：YOLO26-nano-P2（v11.5 權重 `last.pt`，9 類）的 5 個低解析度 LiteRT 匯出組合，另補量 `int8@320` 作為量化感知訓練的延遲上限
> **資料來源**：`adb logcat -s tflite` 實機測試 log、匯出報告 JSON 與判準程式 `judge_deploy_stoploss.py` 的輸出（原始檔存於訓練用程式碼庫 `OneLeaf-dx/detection` 的 `Benchmark/` 與 `tools/`，不在本文件庫版控範圍）
> **撰寫人**：Claude Code

## 1. 摘要

- **依預先登記的門檻，測試裝置上不採用即時辨識，App 只做拍照辨識。** 門檻是 2026-09-08 週會要求的止損標準，於任何新量測之前寫死在判準程式中。
- **五個登記組合的延遲全部過線（28.5 至 38.0 ms），精度全部未過**：test mAP50 最高 0.709，門檻 0.764；每一組都至少有一個類別比參照組合跌超過 0.10。
- **根因是延遲與精度沒有重疊的解析度**：fp32 要降到 224 才進得了 40 ms，但精度在 288 以下斷崖式下滑（288 到 224 掉 0.093）。
- **延遲模型的預測誤差全部在 ±4% 以內**，因此據以在開測前關掉的路線（320 的量化感知訓練、NCNN 與 MNN、拿掉 P2 偵測頭）判斷成立。
- **唯一上限過線的路線是 288 解析度的量化感知訓練**，但精度餘裕僅 0.004，小於 run 間全距 0.021 的五分之一，且不在本次預算內。

## 2. 測試環境與方法

### 2.1 測試裝置

| 項目 | 內容 |
| --- | --- |
| 機型 | OPPO CPH2641 |
| SoC | Qualcomm SM6115（Snapdragon 662） |
| CPU | Kryo 260；指令集無 `asimdhp` 與 `fphp`（不支援 FP16 算術） |
| 系統 | Android 14、arm64-v8a |
| 推論 | LiteRT，CPU only、4 threads、XNNPACK delegate |

### 2.2 採用門檻

門檻於 2026-09-11 登記，**早於本報告的任何量測**，量測後未修改。三條必須同時成立：

#### 表 2-1：即時辨識的採用門檻

| 條件 | 門檻 | 依據 |
| --- | --- | --- |
| 延遲 | 重複量測的最小值 ≤ 40 ms；未含後處理的圖另加 2 ms | 30 FPS 容許下修 5 FPS 的上緣；2 ms 為圖內 TopK 在 320 解析度的實測成本 |
| 精度 | v5.6 test（401 張）上 mAP50 ≥ 0.764 | 現行可交付的 `fp32@320`（0.78511）減 run 間全距 0.021 |
| 逐類 | 任一類 AP50 比 `fp32@320` 低超過 0.10 即否決 | 平均值會掩蓋單一類別崩壞；0.10 為評估集的設計解析度（±2SE ≤ 0.10） |

表 2-1 的精度門檻代表：比現行可交付的組合差到超過一次重跑的隨機變異，就是在用精度換速度。

### 2.3 延遲量測條件

- 每個組合 `num_runs=25`，**交錯重複 3 輪、取最小值**以排除熱尖峰
- 判「通過」單輪即可，因為干擾只會讓數字變大；判「未通過」需 3 輪，或單輪數字扣除實測最大散佈 39% 後仍超過門檻
- 帶額外旗標的量測不計入同一組合

### 2.4 精度量測條件

- 評估集為 v5.6 test 401 張，指標為 TFLite 模型的 mAP50
- 逐類參照為 `fp32@320`（end2end 開、max_det 100）
- `int8` 的校正集為逐類均衡，10 類各 60 張

### 2.5 延遲模型與上限檢驗

以〈[YOLO26-nano-P2 匯出參數與行動端延遲全面掃描報告](yolo26n_p2_export_params_benchmark.md)〉的 12 個實機量測點，對像素數比例 s = (imgsz / 640)² 做線性擬合，先算出每條路線的最好情況；連最好情況都到不了 40 ms 的路線不量測即關閉。

#### 表 2-2：延遲擬合式

| 圖 | 擬合式（ms） | 最大誤差 |
| --- | --- | ---: |
| fp32、end2end 開 | 266.8 × s | 0.6% |
| int8（end2end 被強制關閉） | 8.6 + 138.0 × s | 1.5% |
| fp32、end2end 關 | −9.3 + 283.8 × s | 4.9% |

表 2-2 中 int8 有約 8.6 ms 的固定開銷，因此 int8 相對 fp32 的加速比隨解析度下降而縮小：640 為 1.88 倍，320 只剩 1.49 倍。

#### 表 2-3：各解析度的延遲最好情況

| imgsz | fp32（end2end 開，ms） | int8（含 2 ms 保留，ms） | 可進 40 ms 的圖 |
| ---: | ---: | ---: | --- |
| 320 | 66.4（實測） | 45.5（實測 43.5） | 無 |
| 288 | 54.0 | 38.6 | 僅 int8 |
| 256 | 42.6 | 32.7 | 僅 int8 |
| 224 | 32.6 | 27.5 | 兩者皆可 |

表 2-3 決定了第一階段只量五個組合：fp32 只有 224 可候選，int8 則為 288、256、224。

#### 表 2-4：開測前即關閉的路線

| 路線 | 最好情況 | 關閉理由 |
| --- | --- | --- |
| 320 的量化感知訓練 | 延遲與同解析度的 int8 相同（43.5 ms） | 超過 40 ms |
| NCNN 與 MNN | 需比 `fp32@320` 快 1.62 倍 | 推論框架之間通常只差數十個百分點；224 的 TFLite 本身已預測過線，換框架不增加資訊 |
| 拿掉 P2 偵測頭 | 320 約 42.3 ms | 超過 40 ms，且與降解析度同樣傷害小目標 |
| GPU delegate、NNAPI、`w8a32`、`w8a16` | — | 前一份掃描報告已關閉 |

表 2-4 的路線都在不花任何量測成本的情況下關閉，預算只保留給有便宜前測的路線。

## 3. 數據與分析

### 3.1 判定結果

#### 表 3-1：六個組合的判定

| 組合 | 有效延遲（ms） | 延遲 | mAP50 | 精度 | 逐類否決（相對 `fp32@320`） | 總判 |
| --- | ---: | --- | ---: | --- | --- | --- |
| `int8@224` | 28.5 | 過 | 0.62084 | 未過 | Oily_Spot −0.162、Canker −0.340、Black_Spot −0.293、Scale_Insect −0.302、Aphid −0.129 | 未過 |
| `int8@256` | 32.0 | 過 | 0.70859 | 未過 | Canker −0.215、Scale_Insect −0.194 | 未過 |
| `fp32@224`（end2end 開） | 33.9 | 過 | 0.68938 | 未過 | Canker −0.134、Scale_Insect −0.277、Aphid −0.119 | 未過 |
| `fp32@224`（end2end 關） | 34.0 | 過 | 0.69676 | 未過 | Canker −0.151、Scale_Insect −0.277、Aphid −0.100 | 未過 |
| `int8@288` | 38.0 | 過 | 0.70206 | 未過 | Oily_Spot −0.109、Canker −0.289、Scale_Insect −0.145 | 未過 |
| `int8@320`（上限驗證，非候選） | 44.4 | 未過 | 0.71873 | 未過 | — | — |

表 3-1 中 `Canker` 與 `Scale_Insect` 在五個候選裡全部被逐類否決；fp32 最高只到 0.697，未落入第二階段（一次重訓）的准入區間 0.732 至 0.764，因此第二階段不開。有效延遲為三輪最小值加上未含後處理之圖的 2 ms 保留。

### 3.2 精度：288 以下的斷崖

#### 表 3-2：同一權重在不同推論解析度的精度（PyTorch）

| imgsz | mAP50 | 相對上一格 | `Scale_Insect` AP50 | 過 0.764 | 逐類否決 |
| ---: | ---: | ---: | ---: | --- | --- |
| 640 | 0.80897 | — | 0.668 | 是 | — |
| 320 | 0.77663 | −0.032 | 0.526 | 是 | 無 |
| 288 | 0.76817 | −0.008 | 0.520 | 是（餘裕 0.004） | 無 |
| 256 | 0.73969 | −0.028 | 0.413 | 否 | Scale_Insect −0.136 |
| 224 | 0.67498 | −0.065 | 0.331 | 否 | 五類 |

表 3-2 顯示 fp32 的精度在 288 以下崩落，而延遲要到 224 才過線，兩個條件對 fp32 沒有交集；能同時接近兩邊的只有 256 至 288 的 int8，但靜態量化本身還要再付出代價。

#### 表 3-3：靜態 INT8 量化的精度代價

| imgsz | PyTorch | int8 | 代價 |
| ---: | ---: | ---: | ---: |
| 288 | 0.76817 | 0.70206 | −0.066 |
| 256 | 0.73969 | 0.70859 | −0.031 |
| 224 | 0.67498 | 0.62084 | −0.054 |

表 3-3 的量化代價對解析度不單調，無法外推；受傷最重的是 `Canker`——288 解析度下 PyTorch 只比參照低 0.037，int8 卻低 0.289，是這一類的特徵對 INT8 的啟動值特別敏感，不是解析度造成的。

### 3.3 延遲模型驗證

#### 表 3-4：延遲的預測與實測

| 組合 | 預測（ms） | 實測（ms） | 最小值 | 誤差 |
| --- | ---: | --- | ---: | ---: |
| `fp32@224`（end2end 開） | 32.6 | 45.3、33.9、34.1 | 33.9 | +4.0% |
| `int8@288` | 36.6 | 50.8、37.3、36.0 | 36.0 | −1.5% |
| `int8@256` | 30.7 | 30.3、30.5、30.0 | 30.0 | −2.3% |
| `int8@224` | 25.5 | 58.5、26.5、27.3 | 26.5 | +4.0% |
| `int8@320` | 43.1 | 43.5（09-07）、45.3、43.2、42.4 | 42.4 | −1.6% |

表 3-4 中五個預測的誤差全部在 ±4% 以內，開測前據以關閉其他路線的依據成立。

另有兩件事值得記下：

1. **截距為負的擬合式不可外推。** fp32、end2end 關的擬合式預測 224 解析度為 25.5 ms，實測 32.05 ms（+26%）；改用 end2end 開的擬合式乘以 0.975 估算則為 31.8 ms（+0.8%）。
2. **第一輪量測普遍被熱尖峰汙染**（58.5、45.3、50.8 ms，散佈 34% 至 120%），後兩輪才穩定。若只量一輪，`int8@224` 會被記為 58.5 ms 並誤判為未過——三輪取最小值的協定在此直接改變了結論。

### 3.4 兩個先驗條件

#### 表 3-5：先驗條件的檢查

| 項目 | 結果 | 判定 |
| --- | --- | --- |
| XNNPACK 強制 FP16 | CPU 指令集沒有 `asimdhp` 與 `fphp`；CPU part 為 Kryo 260 | 不量即關閉 |
| 320 量化感知訓練的延遲上限 | `int8@320` 四輪最小 42.4 ms，加保留 44.4 ms | 確定未過 |

表 3-5 的第二項在登記時只有單輪數字、依協定屬「需補量」，本輪補量後確認未過。

### 3.5 唯一上限過線的路線

量化感知訓練產出的是與靜態 INT8 同一種圖，因此它的延遲上限就是 `int8@288` 的實測值，精度上限就是同解析度的 PyTorch 精度。

#### 表 3-6：288 解析度量化感知訓練的上限

| 條件 | 上限 | 門檻 | 餘裕 |
| --- | ---: | ---: | ---: |
| 延遲 | 38.0 ms（實測） | ≤ 40 | 2.0 ms |
| mAP50 | 0.76817 | ≥ 0.764 | 0.004 |
| 逐類 | 最差 Canker −0.037 | 跌幅 ≤ 0.10 | 0.063 |

表 3-6 三條上限都過線，是本次唯一的一條；但未執行，理由有三：

1. **不在本次預算內**：`ultralytics==8.4.121` 沒有量化感知訓練的程式，版本又刻意釘死，只能自寫訓練與轉換流程，工程量以天計。
2. **0.004 的餘裕要求量化感知訓練補回靜態量化損失的全部 0.066**，其中 `Canker` 要從 −0.289 補回到 −0.037；「全部補回」是上限，不是期望值。
3. **0.004 只有 run 間全距 0.021 的五分之一**，即使量化感知訓練做得完美，一次訓練的隨機性就足以讓結果落在門檻的任一側。

## 4. 結論與限制

1. **不採用即時辨識，App 只做拍照辨識。** 依預先登記的門檻判定，較期限 2026-09-22 提前結案，未動用重訓額度。
2. **下一個待決定的是拍照模式要用哪一個組合**：`fp32@320`（64.8 ms、mAP50 0.785）、`fp32@640`（266.3 ms、0.816）、`w8a32@640`（279.5 ms、0.819、3.10 MB），需先由團隊訂出拍照模式可接受的延遲上限。
3. **若日後要重開即時辨識，唯一具體的方向是 288 解析度的量化感知訓練**，並須先接受成功機率不高、餘裕在雜訊以內。

限制：

- **結論只成立於一台裝置**（Snapdragon 662）。更高階的晶片可能讓精度已過線的 `fp32@320` 進入 40 ms，那是不同的問題，需另行登記判準後量測。
- **延遲採三輪取最小值，量的是突發延遲，不是持續負載**；即時辨識屬持續負載，熱降頻的影響未量測。
- **精度數字屬於 v11.5 權重與 v5.6 標註。** 交付權重其後已改為 v5.7（見〈[柑橘病蟲害 YOLO26-nano-P2 v5.7 訓練評估與交付報告](../%E7%97%85%E8%9F%B2%E5%AE%B3%E8%BE%A8%E8%AD%98%E6%A8%A1%E5%9E%8B/20260913_yolo26n_p2_training_report.md)〉）。延遲不受影響，因為架構與輸入尺寸相同；v5.7 的 test mAP50 0.861 是在新的 `Thrips_Damage` 框定義下量得，不可拿來與本報告從 v5.6 標註推出的門檻 0.764 比較。在標註未變動的八類上 v5.7 與 v11.5 表現相同，若依 v5.7 標註重新推導門檻，候選組合與門檻會同步平移，本報告的結論維持。

本報告未涵蓋：

- **第二階段的原生低解析度重訓**：未達准入條件而未開
- **第二台以上的測試裝置與持續負載測試**
- **量化感知訓練的實作**
- **NCNN、MNN 等其他推論框架的實測**
