# YOLO26-nano-P2 天璣 8300 即時辨識門檻實機測試報告

> **報告日期**：2026-09-13
> **評測對象**：YOLO26-nano-P2（v11.5 權重 `last.pt`，9 類）的 fp32 匯出，輸入解析度 320、416、512、640 × end2end 開與關共 8 個組合，於平台 2（Lenovo TB373FU，MediaTek Dimensity 8300）上的 CPU 短時間延遲、CPU 持續負載，以及 GPU delegate 與 NNAPI
> **資料來源**：`adb logcat -s tflite` 實機測試 log、`dumpsys thermalservice` 溫度紀錄與量測 JSON（原始檔存於訓練用程式碼庫 `OneLeaf-dx/detection` 的 `Benchmark/report/`，量測計畫與結果文件為其 `docs/v12.3_*`，不在本文件庫版控範圍）
> **撰寫人**：Claude Code

## 1. 摘要

- **依量測前登記的門檻，平台 2 上即時辨識成立，但只到 320 解析度。** `fp32@320`（end2end 開）短時間 15.0 ms（66.6 FPS），連續跑約 5 分鐘後最後 3 段最差 26.0 ms（38.4 FPS），mAP50 0.785，四項條件全過。
- **精度更高的 `fp32@512` 短時間 39.4 ms（25.4 FPS）過線，連續跑後 63.9 ms（15.6 FPS）未過。** 機身表面溫度在連續推論的頭 30 秒內就從 35 °C 升到 47 °C，越過本機第二級降頻門檻 45 °C；降頻後的延遲是短時間量測的 1.6 至 1.7 倍。**只看短時間量測，會把即時辨識能力高估 60% 至 70%。**
- **相對前一台測試裝置（Snapdragon 662）快約 4.5 倍**，320、416、640 三個解析度的倍率幾乎一致。
- **GPU 的效果取決於 end2end。** 關閉時 511 個節點全數交給 GPU，640 解析度只要 31.8 ms（約 29.6 FPS）；開啟時只有 54/559 個節點上得了 GPU，反而比純 CPU 慢。此數字只量 1 輪、未量持續負載，不構成判定。NNAPI 在所有組合上都比 CPU 慢。
- **結論只成立於這一台平板。** 同晶片的手機散熱較差，不能外推；Snapdragon 662 上不採用即時辨識的結論不變。

### 核心結果總覽

| 組合 | 短時間（CPU） | 連續跑（CPU，最後 3 段最差） | mAP50 | 判定 |
| --- | ---: | ---: | ---: | --- |
| **`fp32@320`（end2end 開）** | **15.0 ms（66.6 FPS）** | **26.0 ms（38.4 FPS）** | 0.785 | **成立** |
| `fp32@416`（end2end 開） | 25.6 ms（39.0 FPS） | 未量 | 0.800 | 不判定 |
| `fp32@512`（end2end 開） | 39.4 ms（25.4 FPS） | 63.9 ms（15.6 FPS） | 0.814 | 不成立 |
| `fp32@640`（end2end 開） | 62.8 ms（15.9 FPS） | — | 0.816 | 不成立 |
| **門檻** | **≤ 40 ms（≥ 25 FPS）** | **≤ 40 ms（≥ 25 FPS）** | **≥ 0.764** | — |

FPS 為 1000 除以每張毫秒數，是模型推論本身的上限，不含相機取像、前處理、後處理與畫面繪製。

## 2. 測試環境與方法

### 2.1 測試裝置

| 項目 | 內容 |
| --- | --- |
| 機型 | Lenovo TB373FU（平板） |
| SoC | MediaTek Dimensity 8300（MT8792） |
| CPU | 4 顆 Cortex-A715 ＋ 4 顆 Cortex-A510；支援 FP16 算術（`asimdhp`） |
| 系統 | Android 16 |
| 推論 | LiteRT，4 threads；CPU 路徑為 XNNPACK |
| 量測狀態 | 螢幕常亮、經 USB 充電中；開始時電量 80%、表面溫度 33.4 °C |
| 降頻門檻 | 表面溫度第一級 43 °C、第二級 45 °C、第三級 48 °C（裝置回報值） |

### 2.2 採用門檻

前三條沿用〈[YOLO26-nano-P2 即時辨識採用門檻實機測試報告](yolo26n_p2_realtime_gate_benchmark.md)〉，另加持續負載一條。四條都在本裝置的任何量測之前登記，量測後未修改。

#### 表 2-1：即時辨識的採用門檻

| 條件 | 門檻 | 說明 |
| --- | --- | --- |
| 短時間延遲 | 3 輪交錯、每輪 25 次推論，取最小值 ≤ 40 ms；未含後處理的圖另加 2 ms | 沿用前一台裝置的標準 |
| 精度 | v5.6 test mAP50 ≥ 0.764 | 與裝置無關，沿用既有量測 |
| 逐類 | 任一類 AP50 比 `fp32@320` 低超過 0.10 即否決 | 416 與 512 為本次補量 |
| **持續負載** | **連續 10 段、每段約 30 秒，最後 3 段每段的平均都 ≤ 40 ms** | **本次新增** |

表 2-1 的第四條是本次新增的：短時間量測取三輪最小值，目的正是排除熱衰減，但即時辨識是持續負載，必須另外量降頻之後的表現。

### 2.3 量測流程

1. **短時間延遲**：8 個組合 × CPU × 3 輪交錯，取最小值。
2. **持續負載**：只量短時間過線者中精度最高的 `fp32@512`（end2end 開），以及 `fp32@320`（end2end 開）。每組連續 10 段，段與段之間只有重新啟動測試程式的間隔；兩組之間冷卻到表面溫度回到 35.4 °C（第二組實際等了 7.6 分鐘）。
3. **GPU delegate 與 NNAPI**：同 8 個組合各 1 輪，記錄節點替換率，不影響判定。

逐類精度的補量在電腦上進行（與裝置無關），使用 v5.6 test 401 張。

- **end2end 關閉的圖，所有節點都交給 GPU**，解析度越高差距越大：320 為 CPU 的 0.80 倍，640 為 0.52 倍。
- **end2end 開啟時，偵測頭的 `ADD`（版本 4）與 INT64 的 `CAST` 不被 GPU 支援**，只有 54/559 個節點上 GPU，整張圖被切成碎片、在 GPU 與 CPU 之間來回搬資料，比純 CPU 慢 1.15 至 1.96 倍。這與前一台裝置上 GPU 被 end2end 算子擋住是同一個機制。
- **NNAPI 把 88% 至 99% 的節點交給 MediaTek 的加速器**，卻比 CPU 慢 1.7 至 5.4 倍，初始化需 11 至 16 秒。
- **`fp32@640`（end2end 關）在 GPU 上是 31.8 ms**，是本次唯一精度最高又在 40 ms 內的數字，但只量 1 輪、未量持續負載，GPU 管線中後處理的實際成本也未量，不構成判定。

## 4. 結論與限制

1. **平台 2 上即時辨識成立，只到 320 解析度。** `fp32@320` 連續跑約 38 FPS，仍高於手機相機預覽常見的每秒 30 張上限，每一張畫面都來得及辨識。
2. **短時間量測不能單獨作為即時辨識的依據。** 本機在 30 秒內就進入降頻，持續延遲為短時間的 1.6 至 1.7 倍；`fp32@512` 短時間 25 FPS 過線，連續跑只剩 16 FPS，約每兩張畫面只能辨識一張。
3. **GPU 搭配 end2end 關閉的圖值得另行驗證。** 640 解析度有機會進入 40 ms 內，但必須連同持續負載與後處理成本一起量。

限制：

- **平台 2 是平板**；同晶片的手機散熱較差，結果不能外推到手機。
- **只有一台平台 2 裝置**，且量測全程經 USB 充電。
- **持續負載判的是 30 秒段的平均**，單張推論偶有碰到 40 ms。
- **FPS 為模型推論本身的上限**，App 完整管線的實際 FPS 會更低。
- **量測使用 v11.5 權重的匯出檔。** 延遲不受權重影響（架構與輸入尺寸相同），但交付權重已改為 v5.7（見〈[柑橘病蟲害 YOLO26-nano-P2 v5.7 訓練評估與交付報告](../%E7%97%85%E8%9F%B2%E5%AE%B3%E8%BE%A8%E8%AD%98%E6%A8%A1%E5%9E%8B/20260913_yolo26n_p2_training_report.md)〉），App 實際採用的組合仍需以 v5.7 權重重新匯出並重評精度。
- `fp32@320`（end2end 關）CPU 的第 2 輪與 `fp32@416`（end2end 關）GPU 未取得結果，原因未查。

- **`fp32@416` 的持續負載，以及 GPU 路徑的持續負載**
