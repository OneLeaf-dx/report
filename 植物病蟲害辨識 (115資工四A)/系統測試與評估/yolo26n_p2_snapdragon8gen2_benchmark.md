# YOLO26-nano-P2 Snapdragon 8 Gen 2 即時辨識門檻實機測試報告

> **報告日期**：2026-09-13
> **評測對象**：YOLO26-nano-P2（v11.5 權重 `last.pt`，9 類）的 fp32 匯出，輸入解析度 320、416、512、640 × end2end 開與關共 8 個組合，於平台 3（ASUS Zenfone 10，Qualcomm Snapdragon 8 Gen 2）上的 CPU 短時間延遲、CPU 持續負載，以及 GPU delegate 與 NNAPI
> **資料來源**：`adb logcat -s tflite` 實機測試 log、`dumpsys thermalservice` 溫度紀錄與量測 JSON（原始檔存於訓練用程式碼庫 `OneLeaf-dx/detection` 的 `Benchmark/report/`，量測計畫與結果文件為其 `docs/v12.3_*`，不在本文件庫版控範圍）
> **撰寫人**：Claude Code
> **更新**：2026-09-15 mAP50 改依 end2end 開或關分別列出；表 3-6 補入天璣 8300 `fp32@416`（end2end 關）的持續負載補量

## 1. 摘要

- **依量測前登記的門檻，平台 3 上即時辨識成立，一樣只到 320 解析度。** `fp32@320`（end2end 開）短時間 31.2 ms（32.0 FPS），連續跑約 5 分鐘後最後 3 段最差 33.5 ms（29.8 FPS），mAP50 0.780，四項條件全過。
- **精度更高的 `fp32@416`（end2end 開）短時間 35.5 ms（28.2 FPS）過線，連續跑後 51.7 ms（19.3 FPS）未過。** 512 與 640 在短時間量測就未過。
- **這是手機。** 前一份〈[YOLO26-nano-P2 天璣 8300 即時辨識門檻實機測試報告](yolo26n_p2_dimensity8300_benchmark.md)〉的結論只成立於平板；本機在同一套門檻下也在 320 成立，但速度較低（連續跑 29.8 FPS，平板為 38.4 FPS）。
- **本機變慢的原因不是過熱。** 全程未進入降頻狀態、表面溫度最高 41.2 °C（降頻門檻 52 °C）；延遲是在不同效能檔位之間階梯式跳動，同一組合的三輪最多相差 1.9 倍。閒置時 CPU 頻率上限就只有硬體上限的 50% 至 59%，來源未查明，量測未調整任何系統設定。
- **GPU 與前一台相同**：end2end 關閉時所有節點交給 GPU，640 解析度 30.6 ms；開啟時只有 54/559 個節點上 GPU。NNAPI 在本機沒有生效。兩者都不構成判定。

| --- | ---: | ---: | ---: | --- |
| **`fp32@320`（end2end 開）** | **31.2 ms（32.0 FPS）** | **33.5 ms（29.8 FPS）** | 0.780 | **成立** |
| `fp32@416`（end2end 開） | 35.5 ms（28.2 FPS） | 51.7 ms（19.3 FPS） | 0.800 | 不成立 |

| `fp32@640`（end2end 開） | 84.8 ms（11.8 FPS） | — | 0.816 | 不成立 |
| **門檻** | **≤ 40 ms（≥ 25 FPS）** | **≤ 40 ms（≥ 25 FPS）** | **≥ 0.764** | — |

FPS 為 1000 除以每張毫秒數，是模型推論本身的上限，不含相機取像、前處理、後處理與畫面繪製。

## 2. 測試環境與方法

### 2.1 測試裝置

| 項目 | 內容 |
| --- | --- |
| 機型 | ASUS Zenfone 10（手機） |
| SoC | Qualcomm Snapdragon 8 Gen 2（SM8550） |
| CPU | 1 顆 Cortex-X3 ＋ 2 顆 Cortex-A715 ＋ 2 顆 Cortex-A710 ＋ 3 顆 Cortex-A510；支援 FP16 算術（`asimdhp`） |
| 系統 | Android 15 |
| 推論 | LiteRT，4 threads；CPU 路徑為 XNNPACK |
| 量測狀態 | 螢幕常亮、充電中；開始時電量 83%、表面溫度 38.8 °C；Android 省電模式關閉 |
| CPU 頻率上限 | 閒置時 Cortex-X3 為 1.59/3.19 GHz（50%）、A715 與 A710 為 1.65/2.80 GHz（59%）、A510 為 1.79/2.02 GHz（89%）；未過熱時即如此，來源未查明 |
| 降頻門檻 | 表面溫度 52 °C（裝置回報值） |

### 2.2 採用門檻

與前一份天璣 8300 報告相同的四條，登記於兩台裝置的任何量測之前，量測後未修改：

1. **短時間延遲**：3 輪交錯、每輪 25 次推論，取最小值 ≤ 40 ms；未含後處理的圖另加 2 ms。
2. **精度**：v5.6 test mAP50 ≥ 0.764。
3. **逐類**：任一類 AP50 比 `fp32@320` 低超過 0.10 即否決。
4. **持續負載**：連續 10 段、每段約 30 秒，最後 3 段每段的平均都 ≤ 40 ms。

精度與逐類結果與裝置無關，沿用前一份報告。

### 2.3 量測流程

1. **短時間延遲**：8 個組合 × CPU × 3 輪交錯，取最小值。
2. **持續負載**：只量短時間過線者中精度最高的 `fp32@416`（end2end 開），以及 `fp32@320`（end2end 開）。每組連續 10 段，段與段之間只有重新啟動測試程式的間隔；兩組開始前都等表面溫度回到 40.8 °C 以下（短時間量測開始時的溫度加 2 °C）或滿 10 分鐘，兩組實際都不需等待。
3. **GPU delegate 與 NNAPI**：同 8 個組合各 1 輪，記錄節點替換率，不影響判定。

- **end2end 關閉的圖，所有節點都交給 GPU**：320 為 CPU 的 0.64 倍，640 為 0.37 倍。`fp32@640` 為 30.6 ms，與前一台平板的 31.8 ms 幾乎相同；416 與 512 在 GPU 上與 320 差不多快。
- **end2end 開啟時只有 54/559 個節點上 GPU**，不支援的算子與前一台相同（偵測頭的 `ADD` 版本 4、INT64 的 `CAST` 等）。剩下的節點由 CPU 接手，結果與純 CPU 相當（0.90 至 1.04 倍），不像平板上慢到 1.15 至 1.96 倍。
- **NNAPI 在本機沒有生效。** 本機的 NNAPI 只提供 Android 內建的參考實作，沒有節點被接走，實際仍在 CPU 上執行，所以表中數字等同 CPU 再量一輪。
- **`fp32@640`（end2end 關）在 GPU 上兩台都約 31 ms**，但只量 1 輪、未量持續負載，GPU 管線中後處理的實際成本也未量，不構成判定。

## 4. 結論與限制

1. **平台 3 上即時辨識成立，只到 320 解析度。** `fp32@320` 連續跑 29.8 FPS，與手機相機預覽常見的每秒 30 張幾乎相同。
2. **兩台高階裝置的結論一致。** 平板與手機都在 320 成立、在下一個解析度的持續負載未過，變慢的機制不同。
3. **短時間量測不能單獨作為即時辨識的依據。** 本機 `fp32@416` 短時間 28.2 FPS 過線，連續跑只剩 19.3 FPS。

限制：

- **只有一支平台 3 裝置**，且 CPU 頻率上限在閒置時就被壓低、來源未查明；結果代表此裝置的出廠狀態，不代表晶片的上限。
- **延遲在效能檔位之間跳動**，同一組合的三輪最多相差 1.9 倍；判定依門檻取最小值與最後 3 段最差。
- **量測全程充電中**（電量 83% 至 98%）；短時間量測未逐輪記錄溫度；手機殼與背景 App 未記錄。
- **持續負載判的是 30 秒段的平均**，單張推論偶有超過 40 ms。
- **FPS 為模型推論本身的上限**，App 完整管線的實際 FPS 會更低。
- **量測使用 v11.5 權重的匯出檔。** 延遲不受權重影響（架構與輸入尺寸相同），但交付權重已改為 v11.5 在 v5.7 資料集上重訓的版本（見〈[柑橘病蟲害 YOLO26-nano-P2 v5.7 資料集訓練評估與交付報告](../%E7%97%85%E8%9F%B2%E5%AE%B3%E8%BE%A8%E8%AD%98%E6%A8%A1%E5%9E%8B/20260913_yolo26n_p2_training_report.md)〉），App 實際採用的組合仍需以交付權重重新匯出並重評精度。

本報告未涵蓋：

- **介於 Snapdragon 662 與這兩台高階裝置之間的中階裝置**
- **解除 CPU 頻率上限（例如切換系統效能模式）後的表現**
- **`fp32@320`（end2end 關）的持續負載，以及 GPU 路徑的持續負載**
- **App 完整管線（相機、前處理、後處理、繪製）的實際 FPS**
- **App 是否依裝置等級開放即時辨識**：屬產品決策，由團隊決定
